# 实时消费边界

[English](mq-delivery.en.md)

nacket 的业务推送和初始化回复只消费本次进程建立消费基线之后的消息。停机一小时再启动时，不读取、解码或扇出这一小时的业务积压。业务历史及缺失数据由业务 REST 接口提供，客户端在重新认证、订阅成功后按业务游标获取。

## Redis Stream

`purpose: push` 和 `purpose: initialization_reply` 必须使用 `delivery: realtime`，`recovery.initialize` 必须为 false。服务实际开始消费时读取 Stream 当前的 `last-generated-id` 和逻辑位置，随后以具体 ID 执行有限批次读取。初始化期间产生的积压同样跳过。

从实际消费开始时的末尾建立基线，不主动回放既有业务历史，不恢复旧消费组、不认领旧 PEL。Stream 尚不存在时，合法初始末尾可以是 `0-0`。在线运行时保存具体游标，不能每次读取都使用 `$`，否则两次读取之间的消息也会丢失。在线普通连接错误撤回该来源依赖资格、保留具体游标与当前进程责任，并按有限退避重试。读取或基线检查出现 `SC_REALTIME_*` 错误时，包括裁剪缺口、基线回退或原文越过脚本边界，会关闭本节点全部路由门禁并使关键消费任务失败，随后进入受管停机；影响不局限于该来源。不得移动游标掩盖缺口。先恢复 broker 与原资源合同、保留 nodeId 和数据卷，再重启并等待持久控制恢复。新进程的实时业务从当次实际消费末尾重新建立基线，不补发停机及未完成区间；所需数据由业务历史或对账恢复。

## Kafka

业务来源必须使用 `auto_offset_reset: latest`。消费组摘要包含 clusterId、scopeEpoch、nodeId、sourceRef 和每次启动新生成的 startupId。即使复用同一 nodeId，也不会继承上次进程的已提交 offset。只给旧消费组设置 latest 不足以实现这个合同。

每个节点独立消费并筛选本地合法接收者；节点之间不竞争同一个工作组。在线再分配和短暂故障遵循当前进程的处理水位，旧 assignment 不得继续提交。过期实时组由 broker 的组保留策略清理，服务不扫描或删除其它组。具体来源要求见 [Kafka 入口](kafka-ingress.md)。

## 容量与时间

实时消费不等于无限吞吐。读前字节预算、批次、并行扇出、候选引用、会话队列和慢连接策略始终生效。消息继续使用首次生产时固定的整数 `createdAt`、`expiresAt`；重投、排队和连接恢复不能延长 TTL。生产者 outbox 在节点恢复后重新发布一条尚未过期的旧业务命令，属于新的 broker 输入，服务仍按消息 ID、原 TTL 和当前权限判断。

## 安全控制状态

路由定义、下线状态、实例围栏、授权版本下界不是业务消息历史，必须从控制权威恢复后才能开放路由。专用 `purpose: authorization_control` 入口仍要求 `delivery: recoverable`，使用稳定组及明确基线；撤权命令不能借跳过积压而失效。该入口有独立的容量、权限和原始命令期限，不向客户端重放历史正文。

业务推送或初始化回复配置为 `recoverable` 会在启动或候选校验时被拒绝。授权控制与实时数据使用不同来源；不能通过热更切换组语义，也不能把旧数据消费进度当作新节点的业务历史恢复点。

Kafka 隔离在途的 DltPending 保留有效 assignment 与原记录责任，不能仅因一条无效记录正在隔离就关闭其它合法会话。DLT 持续失败、容量保护、提交失败、失权和硬暂停仍撤销依赖资格；隔离成功之前不能跨过原记录推进提交。

Kafka 授权命令交给持久控制权威后，在提交结果确定前保持原记录未确认。受管消费组可能在此期间进入 Retrying；napp 的严格就绪策略会使 `/readyz` 暂时返回 503，并拒绝新的客户端认证。这不等于原记录已提交，也不表示所有已有会话都必须关闭：已有会话继续受各自的路由许可、授权和写出门禁约束。客户端应在节点恢复 Ready 后发起新连接，负载均衡和监控应区分暂时摘流与进程退出，不能通过刷新消息期限或忽略撤权进度来维持就绪。

Kafka 控制事务报告终止失败，或控制 topic 合同无法复验时，受管关键任务会触发进程关闭。编排层应在 broker 恢复后重启实例，保留原 nodeId 与数据卷，并等待控制基线恢复及 `/readyz` 成功。进程仍存活时也不能绕过保护门禁。客户端须重新认证、订阅；已过期的 outbox 原记录必须拒绝，不能刷新时间后重投。

## 按业务键处理与连续完成

Redis 业务推送按规范 `ordering_key` 建立有界队列，同键至多一个任务执行，不同键共享 `maxParallelFanouts` 并发名额。一次解析的元数据和原文摘要随责任保留；正文仍共享原始 Bytes，重试不重复解码业务正文。`maxKeyPendingRecords` 限制单键预取，`maxPendingRecords` 限制节点未释放责任；已完成但位于缺口之后的记录仍占名额。

预取位置与连续完成水位分别维护。只有前方所有记录完成本地决定或隔离确认才推进完成水位；一个慢键期间其它键可以完成，但不能借此越过源记录确认。读前保守字节预算保留到整批原文释放。达到键、记录或字节边界时暂停读取；物理 stream 不支持跳过尚未读出的热键，因此容量耗尽会对该来源整体施加背压，这是有界内存的边界。

Kafka 实时推送和初始化回复选择 nafka `KeyOrdered`，同分区不同 key 可并发，同 key 串行；初始化回复仍按其关联键裁决。专用授权控制来源保持 PartitionOrdered。框架执行并发、每键记录/字节、分区、来源、进程和连续提交预算继续生效。单键积压达到框架上限时允许来源背压，不能无限绕过旧提交缺口。

业务记录在原 expiresAt 或 `createdAt + maxRetryAgeMs` 的更早时刻结束投递资格；默认重试年龄上限 60000 毫秒。检查在正文交接容量申请前和实际分发时执行，容量不足不会无限保留已经过期的业务责任。Redis 还限制本地接管责任的最长等待，超时或非法记录必须先完成隔离；隔离不可用则关闭来源资格，不冒充成功。安全控制命令沿用独立恢复和期限合同，不受业务年龄丢弃策略影响。
