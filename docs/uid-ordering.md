# 主体事件顺序与容量

nacket 使用 napp 管理的 napart 默认 Runner。可信 `(tenantId, uid)` 是唯一分区键，所有事件使用同一严格任务类型。相同主体的多个连接、路由和传输在同一节点共享受理顺序；不同节点不构成全局总序。身份必须先通过验证，缺失、空串或仅空白的 uid 不能建立会话。

## 消费与远程等待

认证结果移交、会话确认、订阅意图、取消、授权结果、操作结果、Ready、下行筛选、最终写出许可、回执和连接终态进入同一顺序域。原生业务心跳在该域推进；物理 WebSocket 和 Engine.IO 控制帧不授予或延长身份权限。

本地消费闭包只做同步且有限的状态处理。HTTP、MQ 和实际网络写出在分区外等待；完成后回到原主体分区，复验精确会话、原路由、期限和订阅意图。较晚取消能够使较早订阅的迟到批准失效。远程业务副作用的完成顺序不由本地事件顺序保证，SDK 不应重放结果未知的业务请求。

全局撤权、路由下线和断开会立即收紧门禁，后续清理按主体顺序执行。最终 writer 的许可持续复验原权限，已经进入网络的字节无法撤回。关闭或清理任务被拒绝时，只允许撤销和释放资源；未消费的下线事实计为拒绝，不能绕过分区发送。

## 配置

`nacket.transport.uidEvents` 在启动时冻结，修改需要重启。服务在 UserHook 配置唯一的默认 Runner，部署不要再用 `partition` 重复登记这个 Runner。业务路由不能关闭该顺序模型。

| 配置 | 默认值 | 作用 |
| --- | ---: | --- |
| `partitions` | 32 | 固定原始分区数，必须是二的幂 |
| `queueCapacity` | 256 | 每个原始分区内统一任务类型的队列容量 |
| `maxInflight` | 8192 | Runner 节点在途任务硬上限 |
| `timeoutMs` | 1000 | 从接纳起的本地等待期限，同时受原业务截止点限制 |
| `maxPerUid` | 128 | 同租户、同 uid 跨连接共享的本地事件上限 |
| `maxBytesPerUid` | 8388608 | 单个主体事件闭包保留的逻辑字节上限 |
| `maxBytes` | 268435456 | 节点事件闭包的逻辑字节上限 |
| `controlReserve` | 16 | 完成、取消和关闭的预留条数，不能越过先前事件 |

为保证全部普通事件碰撞到同一原始分区时仍有控制空间，全节点普通事件上限是 `min(queueCapacity, maxInflight) - controlReserve`，默认 240。每个主体还保留至少一个控制名额。每条事件至少计 64 KiB 的控制信息保留量；携带正文的入口另计共享正文及控制区。共享 Bytes 不因此复制，逻辑预算与已有传输实际字节预算同时成立。目录只保留有实际任务责任的主体，释放最后责任后删除。

这些预算覆盖本地排队和消费闭包。远程操作和物理写出的在途责任继续受节点、连接、HTTP/MQ 和 writer 的独立容量约束。取消订阅另有连接级及节点级名额，普通业务操作不能借用。未开始任务取消后，预算随实际载荷释放归还；正在执行的动作不能伪称已回滚。

## 失败与观测

容量、期限、Runner 健康或停机门禁不足时立即拒绝，不转为直接执行、额外 Runner 或无限排队。下行遵守路由慢消费者策略；需要关闭时永久撤销旧会话，重连建立新身份代次。控制任务耗尽时同样拒绝并收紧权限，不承诺永不丢失通知。

nafana 复用 napp 的分区健康与积压来源，并输出固定产品系列：`nacket_uid_events_total{class,outcome}`、`nacket_live_resources{resource="uid_events"}`、`resource="uid_event_bytes"`，以及 `uid_event_wait`、`uid_event_execute`、`uid_event_total` 耗时阶段。最老待决年龄使用 `uid_events` 资源类别。标签不包含 uid、sessionId 或 operationId，监控仍使用独立端口。
